# DevBrain v2.6 Native Validation Candidate

This checkout is `2.6.0-rc.1`. The Codex CLI non-UI scope is recorded stable after nine reviewed native PASS results; UI cases 18, 19 and 41 were excluded by user decision and deferred to v2.7. The overall release remains in validation because UI evidence and Claude evaluation are pending. V2.6 collects fresh host observations, classifies supported failures and calibrates the narrowest responsible module. A preflight block does not establish a model failure or complete that objective.

## Prerequisites and authorization

Start from the existing 12-case [smoke suite](../evaluation/smoke-suite.yaml). Prepare fresh copies with `node evaluation/prepare-smoke.cjs`. Before launching either host, establish command availability, the actual runtime write boundary and a fresh-session setup that excludes evaluator expectations. Use synthetic projects only. Availability alone is insufficient; a preflight receipt records observations and grants no permission.

The initial Codex help probe reported denied startup cache operations outside the repository. The user later authorized Codex runtime/cache, allowing 18 native behavior attempts plus a separate unsupported-model pilot. Claude was absent from PATH but later found bundled in its existing VS Code extension; its external runtime/cache authorization is still pending. Do not change global configuration, repurpose home variables, copy authentication material or install a missing host automatically.

Official [CLI documentation](https://learn.chatgpt.com/docs/developer-commands?surface=cli) describes ephemeral mode as avoiding session rollout persistence. The [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) provides log and SQLite-state path settings. These documented controls do not prove that the observed startup cache is covered; treat isolation as an environment fact to verify before execution.

## Evidence version 2

Scorecards now distinguish `unattempted`, `preflight` and `session` stages. `fresh_session` is null before a host session, true for native fresh evaluation, and false for an existing-session walkthrough. A resumed/unknown-provenance session cannot establish native comparison.

Preflight-blocked cards contain environment observations only, no PASS/FAIL task dimensions and a `host_limitation` category. Their overall BLOCKED status explains why the case cannot start; the report counts zero model sessions. A ready preflight leaves the card NOT_RUN until a session actually starts. Source reads, changes, checks and final claims must be observed in that session before task dimensions can be scored.

Version 1 scorecards retain their historical meaning in v2.5 reports. Do not silently rewrite them as fresh native observations. Use a new candidate batch and version 2 cards; the current validator intentionally rejects old schemas. Input fingerprints still describe the initial fixture/prompt and operational policy, not final edited files or signed evidence.

## Run, score and compare

For each authorized host, run the same 12 cases independently using matched initial inputs and current baseline/skill metadata. Prepare explicit baseline setup with `node evaluation/prepare-smoke.cjs --native-context`; use the separately authorized [manual Codex capture](../evaluation/run-codex-case.cjs) only as described in the [evaluation guide](../evaluation/README.md). Supply only the prompt/project; keep expectations outside context. Record interface/model when known, actual reads, commands, changes, questions and checks. UI quality needs browser evidence. High-risk cases stop before real side effects.

Use the six existing dimensions and PASS/FAIL/BLOCKED/NOT_RUN distinctions. Classify incomplete or failed outcomes through [failure-taxonomy.yaml](../evaluation/failure-taxonomy.yaml): routing, context, precedence, scope, safety, evidence or host limitation. Each classification needs supporting observations and a reason. Missing runtime capability is not automatically a DevBrain rule defect.

Validate the complete batch with `evaluation/validate-results.cjs`. Compare decisions and changes for matched fresh-session pairs, with model/interface/capability limits stated. A well-formed record is not authenticated proof; human review must establish that observations support each score.

## Calibration and completion

First distinguish a fixture/harness defect, a host limitation and observed model behavior. Fix a reproducible harness defect immediately with focused regression checks. For repeated behavior failures, change only the responsible workflow, task route, command or skill description and rerun the affected native cases with fresh inputs. A confirmed critical safety defect warrants a focused supported correction; it does not justify unrelated global rules.

Keep the existing 54 cases unless an observed failure or supported missing requirement needs a new scenario. Avoid baseline growth and additional installed skills solely for evaluation. All maintenance remains repository-local unless the user specifically authorizes a native host's necessary external runtime writes.

Two observed handoff-routing failures justified a 119-character baseline clarification; both passed targeted native reruns. UI attempts exposed renderer and cleanup-scope failures. All three identified generated external cache directories were removed after specific user authorization and verified absent. A focused Windows native probe observed fixture-local temporary paths and a synthetic marker round trip, but timed out before its final response. Final UI cleanup behavior still needs rechecking; never relabel interrupted or failed traces as PASS. Changed profiles require new batches, and targeted reruns do not establish complete host parity.

Promote the overall cross-host candidate to stable v2.6 only after actual fresh host evaluations are recorded for both 12-case sets, failures are explained and material defects corrected/rechecked. The narrower Codex non-UI result is recorded separately and does not change that overall gate. Blocked task evidence remains explicit; a BLOCKED preflight cannot substitute for those native attempts.
