# DevBrain 3.1 reliability

DevBrain 3.1.0 is the stable package for runtime guidance, installation, updates, and local evaluation tools. It provides 30 specialist skills and 113 behavior scenarios. The session baseline is the sole startup module. The evaluation fixtures cover working UI and backend deliverables, prose, and read-only review.

## Run the comparison

These commands describe the 3.1 checkout. Use the [3.2 delivery guide](v3.2-delivery.md) for the current benchmark and reference.

1. Prepare one calibration batch before running the full suite. See the [evaluation guide](../evaluation/README.md) for the maintenance YAML parser.

   ```powershell
   node evaluation/benchmark.cjs prepare 1 copy-default
   node evaluation/benchmark.cjs prepare 2
   node evaluation/benchmark.cjs summarize <batch-id>
   ```

   A full batch with two repetitions creates 96 independent slots (eight tasks, two hosts, three conditions, two attempts). Each starts as `NOT_RUN`. The shell prints the folder under ignored `local/benchmarks/`. Use loopback and synthetic project data when executing the fixtures.

2. The operator reads `operator-index.json` and opens the matching `runs/<id>/project` in a fresh session. Submit the adjacent `prompt.txt` verbatim. Keep the operator index, scores, rubric, and other runs out of model context. Each fixture has its own repository root and equivalent project instructions for both hosts. Use separate, authorized host profiles or equivalently isolated host settings for each condition.

   | Condition | Host context |
   |---|---|
   | `native` | Host defaults and the supplied project instructions. Verify DevBrain context is absent from the loader, discovered skills, memory, and MCP sources. |
   | `reference` | DevBrain v3.0 files from the commit pinned in the suite, delivered through its native loader and skill discovery. |
   | `candidate` | The 3.1.0 checkout under evaluation. Freeze the files and use its native loader and skill discovery. |

   Match the host version, effective model selection, reasoning effort, session mode, tool permissions, and budget within a comparison. Run each group on the same date. Record differences in what was actually loaded. Evaluate Codex and Claude separately. If DevBrain content has to be injected manually, record the method as a separate study. Use the [host matrix](../evaluation/cli-host-matrix.yaml) for automatic discovery and resume/permission boundaries.

3. Verify the fixture and prompt before starting each run. For the `candidate` condition the verifier also compares the active manifest version and profile fingerprint to the batch. Use the batch folder name and the run ID printed in the operator index.

   ```powershell
   node evaluation/benchmark.cjs verify <batch-id> <run-id>
   ```

   After the run, give the reviewer a sanitized response, artifact or diff, relevant screenshots or interactions, and actual check evidence under the opaque run ID. Keep condition labels and revealing paths outside the review packet. The operator retains routing traces separately. Grade each dimension as 0 (failed), 1 (partial), or 2 (met). Scope covers intent, worktree and approval. Correctness covers behavior and factual fidelity. Completion covers requirements and applicable edge states. Verification covers checks and reporting. Clarity covers presentation, copy and usability where relevant.

4. Enter the result in its JSON score file. Record the supporting observation in notes. Use `BLOCKED` for a preflight or material evidence gap. For `SCORED`, supply all five ratings and the environment keys `fresh_session`, `input_fingerprint`, `version`, `model`, `effort`, `mode`, `tools`, `limits`, and `observed_on` (ISO date). Record critical failures even when the run is blocked. Unknown model selection can be recorded as `unknown` and excludes the pair from comparison. The summarizer reports per-dimension differences for matched pairs and preserves blocked, unrun and critical counts.

5. Use a fresh batch after changing the candidate or fixtures. Fix reproducible findings in the narrowest scope that owns them. Summarize observed wins, ties, regressions, and missing comparisons with their denominators and settings. BuildPulse can be a separate full-project benchmark using the same method. Freeze a synthetic starting snapshot and replay identical phase-one and phase-two prompts independently in each condition.

## Native preflight

On 2026-11-18 both executables returned their version locally, Codex CLI 0.169.0 and Claude Code 2.1.325. In a separate preflight both isolated profiles reported no authenticated session. The 3.1 model cases and comparative scores are still unrun.

Bootstrap receipts record the manifest version and the checkout's profile fingerprint. That fingerprint identifies the files targeted by the test. The reviewer still verifies which loader and skills the host actually discovered. A partial response from a failed process, a timeout, an empty reply, or a changed fixture leaves the capture blocked.

## Package verification

Verify repository structure, formatting, harness and release regressions, and install/update behavior on simulated homes. See the [evaluation guide](../evaluation/README.md) for maintenance prerequisites and commands. Use the [installer guide](../install/README.md) to preview installation targets. An existing loader pointing at the same checkout reads the revised runtime guidance in a fresh session.

The isolated release snapshot passed 3,872 repository checks, 39 Node tests, 27 content regression assertions, 371 skill-system checks, and 81 simulated-home installer assertions. Prettier and the diff check passed. The snapshot excluded the optional v3.0 DOCX guides. A fresh 3.1.0 benchmark batch verified all 96 prepared inputs with no model sessions started.

Track live validation independently. Record native discovery, instruction precedence, skill selection, session lifecycle, permission behavior, and matched outcomes on both hosts.
