# DevBrain v2.8: Project Context Architecture

V2.8 makes project-specific context easier to maintain and cheaper to load. It defines a single owner for each fact domain, keeps the host-facing instructions concise, and reads optional visual/API detail only when the task needs it. The project-discovery workflow remains read-only; project context changes use a separate workflow only after an explicit request.

## Ownership model

| File | Canonical content |
|---|---|
| `AGENTS.md` | Shared project instructions, commands, validation, scope, and safety |
| `CLAUDE.md` | Import of `AGENTS.md` plus Claude-only project additions |
| `PROJECT-CONTEXT.md` | Factual product/technical map and pointers to domain context |
| `PROJECT-VISUAL-DNA.md` | UI identity, design-system sources, UI conventions, and visual checks |
| `PROJECT-API-CONTRACT.md` | API contracts, consumers, authorization/data boundaries, and contract checks |

The context index and specialist files are optional. Existing projects may keep facts in their established instructions. Add files only if they reduce confusion or duplicated context. Each fact should have one canonical owner; other files link to it. Project-specific facts stay in the project and never enter DevBrain's global core/runtime.

## Selective loading

Load applicable `AGENTS.md`/`CLAUDE.md` according to the active host. Read the factual project index when broader product/architecture orientation matters. Read Visual DNA for a UI task and API Contract for backend/API/data work. A UI task does not load API detail by default, and an API task does not load Visual DNA by default. This policy does not add files to the session baseline or scan a templates directory during normal coding.

## Setup and maintenance

An explicit project-context setup/update request routes through [project-context setup and maintenance](../workflows/project-context-setup.md). It uses safe project evidence, preserves existing edits, distinguishes verified facts from unknowns, and verifies links/commands. Ordinary [project discovery](../workflows/project-discovery.md) remains read-only and does not generate instructions. Reconciliation handles material conflicts; it does not silently alter API, data, security, deployment, or other protected behavior.

The template ownership and adoption guide is [project-templates/README.md](../project-templates/README.md). The Markdown/YAML templates are examples, not a required project structure.

## Release scope and validation limits

V2.8 changes project templates, their routing, documentation, and behavior evaluations. It does not change the installer, bootstrap payload, runtime baseline, skills, source DOCX, or installed host configuration. Repository-level validation can verify paths, ownership rules, routing, regressions, and installer behavior using simulated homes. These checks do not prove live model behavior. The separate v2.7 Codex/Claude CLI compatibility matrix remains pending beyond its partial bootstrap captures; v2.8 makes no claim of full native host parity.

## Validation record

On 2026-10-28, repository validation passed 2,481 content checks across 172 files and 14 YAML files; all 59 scenarios were structurally valid. The four PowerShell scripts parsed, the DOCX path/key scan passed, and `git diff --check` passed. The runtime baseline remained 8,433 characters, 1,125 words, and an estimated 2,109 tokens.

Content regression tests passed 22 assertions and rejected all 20 intentional regressions. The Node evaluation harness passed 32/32 tests. Installer integration passed 35 assertions with all writes confined to ignored `local/` fixtures. Smoke preparation created 24 synthetic Codex/Claude projects with scorecards still `NOT_RUN`; it did not launch a host. These results support stable status for the project-context scope. Native Codex/Claude behavior and full v2.7 CLI compatibility remain pending and are not claimed by this release.
