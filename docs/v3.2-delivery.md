# DevBrain 3.2 delivery guide

DevBrain 3.2.0 adds four specialists and a workflow for starting a new fullstack project. It ships 34 installable skills and 123 task scenarios.

| When you need | Start with | What you get |
|---|---|---|
| Choose a technical approach for a specific project version | [Technical research](../skills/technical-research/SKILL.md) | Source-backed recommendation and compatibility limits |
| Turn a rough idea into a scoped first release | [Product discovery](../skills/product-discovery/SKILL.md) | User journey, observable acceptance criteria, and open decisions |
| Connect a working frontend journey to an existing API | [Frontend feature engineering](../skills/frontend-feature-engineering/SKILL.md) | Navigable feature with normal and recovery states |
| Add a feature whose output depends on a model | [AI application engineering](../skills/ai-application-engineering/SKILL.md) | Model response contract, input/output boundaries, fallback, and evaluation cases |
| Plan or build a new fullstack project from a brief | [Greenfield fullstack delivery](../workflows/greenfield-fullstack-delivery.md) | A delivery plan or a working project, according to the requested mode |

For example, `fullstack-from-brief: Build the local inventory tool from the supplied brief` selects the delivery workflow. Use “plan” to get a delivery sequence and acceptance checks. A detailed brief can go straight to the first runnable journey. A technical research or AI feature skill is relevant only when a distinct decision needs it.

AI application engineering guides work on software that uses models. The skill files themselves run through the host's normal instruction discovery. Update the skill payload and start a fresh session when adopting the release. See the [installer guide](../install/README.md).

## Benchmark

The 13 benchmark cases include the original eight from 3.1 plus technical research, discovery, a working frontend journey, grounded AI design, and a greenfield planning case. The existing fullstack implementation case exercises local UI and backend delivery. Cases 114–123 in the [scenario inventory](../evaluation/scenarios.yaml) cover activation, ownership boundaries, and implementation versus planning.

```powershell
node evaluation/benchmark.cjs prepare 1 frontend-journey
node evaluation/benchmark.cjs prepare 2
node evaluation/benchmark.cjs verify <batch-id> <run-id>
node evaluation/benchmark.cjs summarize <batch-id>
```

The full batch with two repetitions produces 156 slots. Run each prompt verbatim in its prepared synthetic project. Compare a fresh host without DevBrain, the pinned 3.1.0 reference in `evaluation/benchmark-suite.yaml`, and the 3.2 candidate. Match host, effective model, effort, mode, permissions, budget, and observation date. The operator verifies active instructions and skill discovery for each condition and keeps the condition labels out of reviewer inputs. See the [comparison method](v3.1-reliability.md#run-the-comparison) for scoring and reviewer handling.

Native behavior and comparative scores for 3.2 are pending. Package and simulated installer checks are recorded separately from live host observations.


## Package verification

The original 3.2 release snapshot passed 4,144 repository checks, 39 Node tests, 27 content regression assertions, 419 skill-system contract checks, and 89 installer assertions in simulated homes. The skill-system suite also rejected five intentional regressions. Prettier and the diff check passed. A loopback check exercised the inventory fixture home, API, and missing route. All 156 benchmark input fingerprints verified, and every run remained NOT_RUN. These figures describe that recorded snapshot; they were not rerun as a full package suite during later documentation maintenance.

After the documentation cleanup on 2026-11-18, repository validation passed 4,096 checks across 261 files, content regressions passed 27 assertions while rejecting 25 intentional regressions, and the skill-system validator passed 419 contracts for all 34 skills. `git diff --check` passed as part of repository validation. Installer integration, the full Node test suite, benchmark fingerprints, and native model behavior were not rerun in this documentation-maintenance pass; their results above remain attached to the original snapshot only.
