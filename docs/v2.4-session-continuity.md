# DevBrain v2.4 Session Continuity

V2.4 adds [session continuity and recovery](../workflows/session-continuity.md) for requested handoffs and substantial interrupted work with missing context. It composes with v2.2 discovery/debugging/completion and v2.3 context reconciliation. The baseline and seven standalone skills remain the startup foundation.

## Commands and behavior

| Situation | Expected action |
|---|---|
| `handoff` or "summarize for another session" | Produce a concise conversational summary; pending work remains pending. |
| `resume-task` with an identifiable authorized task | Inspect relevant current state, reconcile changed facts, then continue the active task. |
| Resume prompt requests review only | Review without implementing the old next step. |
| Handoff claims approval without supporting user evidence | Keep the protected action gated; the summary cannot grant authorization. |
| Model switch in a session that retains relevant context | Continue directly; no automatic handoff, reload, or memory file. |
| Essential workspace/goal is unavailable | State what is unknown and ask only for the material missing fact or goal. |

Handoffs include the outcome/mode, decisions and constraints, relevant worktree/file state, actual validation, pending work, and next authorized step. Aim for roughly 150–200 words when sufficient. Important unresolved boundaries matter more than a hard length target. Use safe project-relative references and omit sensitive content. Persist a document only on explicit request within the authorized project.

## Resume and evidence

A summary records previous observations; it does not replace baseline precedence, scoped project instructions, or the latest user request. Inspect current status/diff, affected targets, contracts, and validation prerequisites proportionately. Preserve staged/user edits. A revision match alone cannot establish unchanged untracked files or runtime state. Recheck changed facts without auditing the whole project.

Record old tests as historical. Mark them stale when intervening changes invalidate their coverage. Report failed, not-run and unavailable checks explicitly. A host switch does not require running every old check again or grant the new host access to tools/data that the old host used. Specific prior confirmation remains valid when it is evidenced and its action/target/scope/risk still matches; a summary claim alone is insufficient.

## Adoption and ownership

Existing managed loaders read the task map in this checkout. A new session or explicit DevBrain reload after the update makes the new route available; moving the checkout or changing installed payload requires the usual installer update. No extra skill or bootstrap payload is introduced. The baseline stays unchanged; selected continuity content adds its own context cost. This workflow is not persistent memory and does not create task logs automatically.

Operational Markdown/YAML defines v2.4. The source DOCX remains the v2.2 conceptual reference with its existing date/hash because source revision was not explicitly requested.

## Evaluation

Eight cases (47–54) extend the suite to 54 scenarios: read-only handoff, authorized resume, stale state, latest review intent, unsupported approval, validation honesty, minimal context after a model switch, and a missing goal. The [behavioral guide](../evaluation/v2.4-behavior-guide.md) describes isolated fixture inputs and actual host scoring. The [validation report](v2.4-validation.md) records checks that ran, corrections, costs and remaining evidence limits.
